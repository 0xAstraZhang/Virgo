# 故障排查与恢复

[文档首页](../README.md) · [English](../../en/guides/troubleshooting.md)

## 从可见故障开始

| 现象 | 检查方向 |
| --- | --- |
| 全屏启动失败 | 使用交互终端和受支持的 `TERM`，或改用 `--ui plain` |
| 模型列表为空 | 等待启动刷新完成后重开 `/model`，检查 `/login`，或直接 `/model provider/id` |
| 更换服务地址后认证失败 | 为新协议／地址重新登录，保存的凭据与连接绑定 |
| 配置的 Shell 不可用 | 用 `/shell` 选择或指定受支持的可执行文件；Virgo 不会静默替换语言 |
| 定时任务未执行 | 检查本地时间、持久化及 Virgo 是否持续运行，参见[重启语义](schedules.md#持久化与重启) |
| 保存历史失败后暂停 | 保持当前进程运行，解决文件系统问题，在切换或退出前查看诊断 |

`/diagnostics` 显示日志位置和最近十条错误。`/diagnostics <error-id>` 根据唯一 ID 或前缀，显示当前实例最近一百条记录中的完整 JSON。重启后应直接读取 JSONL 日志，此命令不会扫描全部历史日志。

首次错误发生时，日志写入 `~/.virgo/logs/`，或 `$VIRGO_HOME/logs/`。每个实例使用独立的 `harness-<UTC时间>-<进程号>-<ID>.jsonl`。`/new` 沿用该实例日志，各记录保留原始会话 ID。`--no-session` 仍会生成诊断日志。

## 阅读诊断

| 字段 | 含义 |
| --- | --- |
| `error_id` | 跨边界传递时复用的稳定错误标识 |
| `phase`、`code`、`kind` | 发生阶段、机器可读分类，以及重试／溢出／致命／阻止类别 |
| `exception_type`、`cause_chain`、`traceback` | 实际异常、采集的原因链和堆栈位置 |
| `context` | 白名单关联元数据：会话、Runtime、Agent、工具调用、模型调用、尝试次数、耗时和 HTTP 信息 |
| `log_path`、`logging_error` | 记录保存位置，或日志失败原因 |

模型错误先看实际 API、HTTP 状态、request ID 和已有的重试信息；本地错误先看阶段、异常和原因链。后续重试成功不会删除之前的失败。异常消息是证据，不代表已经确认唯一根因。

日志默认每个文件最多 5 MiB，并保留两个轮转文件，必要时读取同名 `.1` 和 `.2`。这是单实例限制，不会统一清理过去实例的日志。平台支持时，新文件和目录使用受限权限。日志本身失败后，会尝试向 stderr 输出脱敏记录，不覆盖原始错误。

诊断不会主动收集 frame locals、源代码行、完整请求正文、headers、系统提示或对话消息，凭据和敏感元数据会脱敏。但应用错误消息和服务 stderr 仍可能含有业务文本，分享前应检查。此规则不改变会话历史和完整工具输出文件原有的存储约定。

## 模型可查看的证据

失败工具结果可追加最多 2 KiB 的诊断摘要，原有结果内容和 ID 保留。若当前 Runtime 暴露了该工具，模型可以通过 `diagnostic_get(error_id, section, cursor)` 按需取证。

| 栏目 | 证据 |
| --- | --- |
| `summary` | 白名单字段和关联上下文 |
| `causes` | 已采集异常链及有界位置 |
| `trace` | 已采集堆栈文本 |
| `stderr` | 已收集且脱敏的 MCP stderr |
| `attempts` | 同一逻辑调用及用途下，仍被保留且获授权的失败 |
| `related` | 已明确传播的关联诊断 |

查询使用完整 ID，不接受任意路径或 ID 前缀。权限属于调用 Runtime，共享记账存储或在界面选中其他对话不会授予访问权。默认保留 100 条证据和 1000 个已授权 ID，分别返回 `not_found`、`expired` 或 `unavailable` 等明确状态。完整 JSON 响应每页最多 8 KiB，游标绑定错误、栏目和证据快照。

`features.diagnostics=false` 关闭模型工具、结果摘要和诊断通知，但保留独立日志。诊断在正常模型请求边界追加；收集证据不会自行启动模型轮次，也不会改写旧消息。

## 执行失败不等于没有副作用

`details.execution` 记录工具是否已经启动，以及返回成功、错误或未知结果；`details.transport` 记录 MCP 派发和响应状态。工具成功后的结果钩子失败，不会撤销原操作。超时命令、失败的子 Agent 或丢失的远程响应，都可能已经修改文件或外部状态。重复操作前应先核对结果。

Provider 重试仍由 Runtime 的现有策略统一控制。有效 `Retry-After` 是最短等待，`retry.maxWaitSeconds` 限制累计等待。已经启动服务端原生网页操作的请求，不会作为“不支持能力”的回退而自动重放。

## MCP 恢复

`mcp_status` 只读取本地状态，不联系服务。模型的 `mcp_reconnect(server, error_id)` 要求当前连接代次中该服务的已授权诊断，并经过正常权限检查。它不能中断进行中的调用，也不能与已有候选恢复并发。计划模式不允许重连。

替代连接必须完成初始化、工具列表和 schema／名称验证后才能发布。schema 不变时替换连接；schema 改变时在安全的模型请求边界发布。显式受限的子 Runtime 工具列表不会因此增加能力。候选无效时保留原连接和工具。

在没有远程工具调用成功的情况下，最多允许两次恢复尝试；仅握手成功不会重置预算。重连从不重放失败调用。如果请求已进入 `sending` 或 `sent` 而响应丢失，业务结果仍未知。人工 `/mcp reconnect` 可重新加载较大范围的配置，也会遵守活动调用边界。

## 会话保存失败

写入失败后，会话存储保留逻辑上的内存记录，并通过独立日志报告原始原因。调度暂停，同时通知所属 Runtime，避免继续执行却不断积累未保存历史。切换界面不会修复失败存储，诊断通知也不能清除取消或保存失败状态。在恢复需要的未保存信息前，应避免关闭进程。
