## 启动采样方法

下表每列均为**五个新进程样本**，来自同一 Linux 工作区、CPython 3.13.5 和未变化的 `uv.lock` 依赖环境；文件系统／依赖缓存已预热。[`ci/measure_startup.py`](../../../ci/measure_startup.py) 使用离线 `faux` 模型、空临时工作目录与用户目录、`refresh_models=False`、`extensions=False`，且不配置 MCP 服务器。不使用凭据，也不调用真实厂商。

基线装配重构前的默认功能；其余两列选择本 PR 实现的 `minimal` 或 `coding`。这是会话构造采样，不是完整 CLI 首屏耗时或首次模型 Token 延迟。所有样本值和模型可见工具名保留在[原始 JSON](../../ci-results/core-plugins-startup-2026-11-14.json)。

## 观察结果

除标注范围的行外，均为中位数。每个耗时字段单独汇总，因此导入和构造的中位数之和不一定等于总耗时中位数。

| 指标 | 基线默认装配 | `minimal` | `coding` |
| --- | ---: | ---: | ---: |
| 导入耗时，ms | 99.668 | 77.031 | 71.528 |
| 会话构造耗时，ms | 36.729 | 13.462 | 26.286 |
| 导入＋构造耗时，ms | 136.398 | 91.227 | 97.750 |
| 总耗时观察范围，ms | 104.095–147.591 | 84.759–103.487 | 94.853–119.569 |
| 已导入 Python 模块数 | 346 | 312 | 340 |
| 已导入 Virgo 模块数 | 88 | 64 | 82 |
| 构造后的活动 Python 线程数 | 2 | 1 | 1 |
| 模型可见工具数 | 28 | 6 | 14 |
| 序列化工具 Schema 字符数 | 13,430 | 2,950 | 7,277 |
| 基础系统提示字符数 | 926 | 682 | 926 |
| Linux 进程最大 RSS，KiB | 27,284 | 24,968 | 26,504 |

在当前环境中，`minimal` 暴露 `read`、`write`、`edit`、`glob`、`grep` 和所选的 `bash`。`coding` 另外暴露 `diagnostic_get`、`todo_write`、`ask_user`、`agent`、`job_output`、`job_kill`、`web_search`、`web_fetch`。没有服务器配置时不出现 MCP 管理工具；两个候选预设均不再启动原调度器线程。

这组小样本只展示当前配置的资源规模，不是普遍的启动性能保证。进程调度、缓存、Shell、依赖、资源配置和真实连接都会影响结果。RSS 是进程高水位，并非保留堆大小，其单位在其他系统上也可能不同。字符数不是模型 Token 数或计费量。`coding` 基础提示长度未变，也不代表厂商原生请求字节完全相同；相关契约由既有请求／前缀场景验证。

## 复现

两个 checkout 使用同一解释器和锁定依赖。候选版本的每条命令分别在新进程中执行五次：

```bash
uv run --no-sync python ci/measure_startup.py --profile minimal
uv run --no-sync python ci/measure_startup.py --profile coding
```

测量脚本是本次新增。测量基线时，使用同一个脚本和解释器，把 `PYTHONPATH` 指向独立的 `47e1757` checkout，并省略 `--profile`。脚本使用一次性工作区和用户目录，无需现有用户数据。保留每次输出，对每个数值字段独立计算中位数；不要用冷安装和热缓存环境直接对比，也不要丢弃较慢样本。

## 真实模型质量仍需另行评估

本次没有测量真实厂商的编程成功率、人工介入率、Token、费用或任务完成延迟。可复现的后续评估应固定仓库快照、模型／版本和推理强度、提示、验收条件、权限与预算，对基线和候选运行相同编程任务，记录成功、工具失败／恢复、人工介入、模型调用、耗时与费用。

确定性验收证明的是被执行到的运行时行为。工具数、代码行数或启动毫秒数的减少不能替代真实编程质量，也不足以断言模型编程能力得到提升。
