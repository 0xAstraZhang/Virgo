# Execution boundaries and sandbox

> Virgo's sandbox is a **guardrail** against occasional model mistakes. It keeps writes inside the current workspace, protects high-sensitivity credentials and Virgo project settings, and asks before out-of-scope or high-risk operations. It is **not** a security boundary against malicious code, deliberate evasion, or prompt-injection attack chains. Run Virgo in a container or VM when working with untrusted repositories or content.

Linux, macOS, supported Windows 11 (`null.sys` Feature `60692039`), and Windows + WSL2 are all **Tier 1** platforms defaulting to **Workspace-Edit**. Supported Windows 11 uses Standard AppContainer (unelevated, no Administrator privileges required); older Windows builds without `ALL APPLICATION PACKAGES` (`S-1-15-2-1`) on `\Device\Null` default to **No-Limit** and prompt you to use **1. WSL2**, **2. No-Limit**, or **3. Update Windows**. WSL2 uses the Linux sandbox backend and remains a Tier 1 option for older Windows builds, Linux toolchains, or localhost/loopback (`127.0.0.1`) access inside sandboxed commands. See [native Windows sandbox](windows-sandbox.md) and [WSL2 setup](wsl2.md).

## What the guardrail covers

1. **Workspace scoping and `.virgo` write confirmation**: By default, **Workspace-Edit** allows writing inside the live project workspace—including `.git`, `AGENTS.md`, `CLAUDE.md`, and workspace-local `.venv` environments so normal `git add / commit / checkout / pull`, documentation maintenance, and package installs work without friction. Modifying project `.virgo` (`PROTECTED_NAMES = (".virgo",)`) triggers a confirmation prompt (and is read-only inside unapproved Shell commands when `.virgo` exists, or even when absent on macOS Seatbelt). Broker file tools (`read`, `write`, `edit`, `glob`, `grep`) enforce `PermissionPolicy` directly—defaulting to the workspace root and prompting once per external path prefix—with final-component `O_NOFOLLOW` and atomic temp-file replacement.
2. **High-sensitivity credential and environment protection**: Virgo's private directory (`~/.virgo` or `$VIRGO_HOME`) and high-sensitivity credential paths (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube`, `~/.azure`, `~/.config/gcloud`, `~/.config/gh`, `~/.netrc`, `~/.npmrc`, `~/.pypirc`, `~/.git-credentials`, `~/.docker/config.json`) are hard read- and write-denied across Linux, macOS, and native Windows and cannot be granted via `request_permissions`. Sandboxed Shell commands strip credential and shell-injection environment variables (`*_API_KEY`, `*_SECRET*`, `*_TOKEN`, `*_PASSWORD`, `OPENAI_*`, `ANTHROPIC_*`, `AWS_*`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK`, `VIRGO_HOME`, `PYTHONPATH`, `BASH_ENV`, `LD_PRELOAD`, etc.) while preserving `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` / `ALL_PROXY`, `SSL_CERT_FILE`, and language toolchain variables, plus a session-reused cache directory (`XDG_CACHE_HOME`, `UV_CACHE_DIR`, `PIP_CACHE_DIR`, `NPM_CONFIG_CACHE`). **Read-Only** disables Shell networking by default; **Workspace-Edit** enables outbound Shell networking.
3. **High-risk command confirmation**: High-cost or irreversible Shell commands (`git push --force`, pushes to protected branches, `git reset --hard`, `git clean -f`, `curl | sh`, recursive deletion outside the workspace, deploy/publish, cloud resource deletion, and destructive SQL/Redis statements invoked through database/cache CLIs) require explicit one-shot user confirmation in **all** modes (including **No-Limit**, unless `permissions.confirmHighRisk` is set to `false` in No-Limit).
4. **Visible failure without silent downgrade**: If the native sandbox backend cannot be established, Virgo fails closed with an error, offers an explicit one-shot **No-Limit** option in interactive sessions (leaving the session mode unchanged), and never silently falls back to Host or automatically replays a command that may have started.

## What is out of scope

- Resisting a model actively attempting to evade the guardrail.
- Defending against crafted attack chains (TOCTOU races, pre-planted symlink/hardlink chains, case-folding tricks, malicious packages/dependencies, malicious concurrent host writers, or OS/kernel bugs).
- Defending against prompt-injection attack chains (though hard-denying private credentials, confirming `.virgo` writes, stripping untrusted project configs, and Read-Only network isolation still mitigate common accidental and injection impact).
- Identical isolation strength across all operating systems.

## Platform backends and honest differences

- **Linux (Tier 1 — `bubblewrap`)**: Requires system `bwrap` and unprivileged user namespaces (`--unshare-all --unshare-user --disable-userns --cap-drop ALL`, with `--info-fd` startup acknowledgement and no `libseccomp` runtime dependency). Mounts the host filesystem read-only (`--ro-bind / /`) with real read-only `$HOME` so user-installed toolchains (`~/.cargo`, `~/.rustup`, `~/.local`, `nvm`, `pyenv`, etc.), `AF_UNIX` local sockets, `AF_NETLINK`, and `io_uring` work seamlessly, while masking high-sensitivity credential directories/files (`--perms 000 --tmpfs` / empty read-only file mounts) and mounting the workspace, session cache, and per-command `TMPDIR` writable. Existing unapproved `.virgo` directories are bind-mounted read-only; absent `.virgo` creation inside Shell is a Linux bind-mount limitation, while Broker file tools and untrusted project settings stripping still protect it.
- **macOS (Tier 1 — Seatbelt)**: Probes `/usr/bin/sandbox-exec` once per executor and launches commands directly in a dedicated POSIX process group (`HostProcess`, cleaning up same-process-group children via `waitid(WNOWAIT)` / `kqueue` + `os.killpg`). Allows read-only host path access (`/` and read-only `$HOME`), grants writes and local `AF_UNIX` sockets inside the workspace, session cache, and per-command `TMPDIR`, write-denies unapproved `.virgo` (both existing and absent), and hard-denies all high-sensitivity credential paths. A descendant that explicitly calls `setsid()` or changes process groups is not reaped automatically on macOS (same as POSIX Host commands).
- **Native Windows (Tier 1 — Standard AppContainer `windows-appcontainer`)**: Runs unelevated on local NTFS and Windows 11 ReFS Dev Drive volumes (`DRIVE_FIXED` + `FILE_PERSISTENT_ACLS`) via direct `CreateProcessW` (`PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` + `HANDLE_LIST` + `JOB_LIST`) using a session-level single AppContainer SID, single-call OS-propagated `SetNamedSecurityInfoW` inheritable ACEs, automatic session read-only ACEs for workspace `.venv` base Python and user-owned toolchains on `PATH` (`~/.cargo`, `~/.rustup`, `~/.local`, `scoop`, `%LOCALAPPDATA%\Programs\<Tool>`, `%LOCALAPPDATA%\uv`, etc.), Job Object (`KILL_ON_JOB_CLOSE`) process-tree cleanup, a session-local `DefineDosDeviceW` virtual drive when workspace ancestors lack `S-1-15-2-1` (such as `C:\Users`), and a write-ahead JSON journal (`%LOCALAPPDATA%\Virgo\sandbox-sessions\`) with automatic startup crash recovery. Existing unapproved `.virgo` is write/rename/delete-protected via `protected_readonly` (`SE_DACL_PROTECTED` + explicit `ALLOW RX`) and automatically restored if approved mid-session. Private user credential directories (`~/.virgo`, `~/.ssh`, `~/.aws`, etc.) are denied by default NTFS ACLs (`$HOME` cannot be used as a workspace). Read-Only (`capabilities=()`) blocks all networking; Workspace-Edit (`internetClient` + `privateNetworkClientServer`) allows outbound egress while **localhost/loopback (`127.0.0.1` / `[::1]`) remains blocked** without Admin (use one-shot No-Limit or WSL2 for local dev servers/databases/proxies). Non-AAP admin/SYSTEM-owned runtime roots without `WRITE_DAC` fail closed with `windows_runtime_inaccessible`. See [native Windows sandbox](windows-sandbox.md).
- **Windows + WSL2 (Tier 1)**: Uses the Linux `bubblewrap` backend inside WSL2; ideal when Linux toolchains or sandboxed localhost/loopback access are preferred. See [WSL2 setup](wsl2.md).

## Broker tools, output storage, and trusted integrations

- **File tools** run in the Broker directly against `PermissionPolicy` (no separate OS sandbox helper process), keeping cold start under 5 seconds and per-Read latency constant regardless of workspace size.
- **Command outputs** are piped to the Broker's session-persisted `OutputStore` under `<VIRGO_HOME>/outputs/session-<id>` (readable via `read_output` after session resume, cleaned up on session trash and by a 7-day TTL; untruncated foreground commands leave no spool files behind).
- **Trusted user integrations** (Python extensions, command hooks, and stdio MCP servers) run on **Host**; trust is established when you install them or trust a project (`extensions.trustedProjects` / `--trust-project-extensions`). Untrusted project `hooks`, `mcpServers`, `.virgo/mcp.json`, `providers`, and `extensions` are ignored before merging onto user settings.
