# Execution boundaries and sandbox

[Documentation](../README.md) · [Project home](../../../README.md) · [简体中文](../../zh-CN/guides/sandbox.md)

> Virgo's sandbox is a **guardrail** against occasional model mistakes. It keeps writes inside the current workspace, protects high-sensitivity credentials and Virgo project settings, and asks before out-of-scope or high-risk operations. It is **not** a security boundary against malicious code, deliberate evasion, or prompt-injection attack chains. Run Virgo in a container or VM when working with untrusted repositories or content.

Linux, macOS, updated Windows 11, and Windows + WSL2 are all **Tier 1** platforms defaulting to **Workspace-Edit**. Older Windows builds that do not support unelevated Standard AppContainer default to **No-Limit** with a one-time notice offering **1. WSL2**, **2. No-Limit**, or **3. Update Windows**. See [Native Windows sandbox](windows-sandbox.md) and [WSL2 setup](wsl2.md) for platform specifics.

## What the guardrail covers

1. **Workspace scoping and `.virgo` write confirmation**: **Workspace-Edit** allows writing inside the live project workspace—including `.git`, `AGENTS.md`, `CLAUDE.md`, and workspace-local `.venv` environments so normal Git operations, documentation edits, and package installs run without friction. Modifying project `.virgo` (`PROTECTED_NAMES = (".virgo",)`) requires confirmation (and is read-only inside unapproved Shell commands when `.virgo` exists, or even when absent on macOS Seatbelt). Broker file tools (`read`, `write`, `edit`, `glob`, `grep`, `present_file`) enforce `PermissionPolicy` directly—prompting for exact resolved file paths on `read`/`write`/`edit`/`present_file` and directory prefixes on `glob`/`grep`—with final-component `O_NOFOLLOW` and atomic temp-file replacement.
2. **High-sensitivity credential and environment protection**: Virgo's private directory (`~/.virgo` or `$VIRGO_HOME`) and high-sensitivity credential paths (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube`, `~/.azure`, `~/.config/gcloud`, `~/.config/gh`, `~/.netrc`, `~/.npmrc`, `~/.pypirc`, `~/.git-credentials`, `~/.docker/config.json`) are hard read- and write-denied across Linux, macOS, and native Windows and cannot be granted via `request_permissions`. Sandboxed Shell commands strip credential and loader-injection environment variables (such as `*_API_KEY`, `*_SECRET` / `*_SECRET_*`, `*_TOKEN`, `*_PASSWORD`, `OPENAI_*`, `ANTHROPIC_*`, `AWS_*`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK`, `VIRGO_HOME`, `PYTHONPATH`, `BASH_ENV`, `LD_PRELOAD`) while preserving `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` / `ALL_PROXY`, `SSL_CERT_FILE`, and language toolchain variables, plus a session-reused cache directory (`XDG_CACHE_HOME`, `UV_CACHE_DIR`, `PIP_CACHE_DIR`, `NPM_CONFIG_CACHE`). **Read-Only** disables Shell networking by default; **Workspace-Edit** enables outbound Shell networking.
3. **High-risk command confirmation**: Irreversible or high-cost Shell commands (`git push --force`, pushes to protected branches, `git reset --hard`, `git clean -f`, `curl | sh`, recursive deletion outside the workspace, deploy/publish, cloud resource deletion, and destructive SQL/Redis statements invoked through database/cache CLIs) require explicit one-shot user confirmation in **all** modes (unless `permissions.confirmHighRisk` is set to `false` in **No-Limit**).
4. **Visible failure without silent downgrade**: If the native sandbox backend cannot be established, Virgo fails closed with an error, offers an explicit one-shot **No-Limit** option in interactive sessions (leaving the session mode unchanged), and never silently falls back to Host or automatically replays a command that may have started.

## What is out of scope

- Resisting a model actively attempting to evade the guardrail.
- Defending against crafted attack chains (TOCTOU races, pre-planted symlink/hardlink chains, case-folding tricks, malicious packages/dependencies, malicious concurrent host writers, or OS/kernel bugs).
- Defending against prompt-injection attack chains (though hard-denying private credentials, confirming `.virgo` writes, stripping untrusted project configs, and Read-Only network isolation still mitigate common accidental and injection impact).
- Identical isolation strength across all operating systems.

## Temporary files in sandboxed Shell commands

- On Linux, WSL2, and macOS, host `/tmp` is read-only by default. Use `$TMPDIR` for temporary files. `TMPDIR`, `TMP`, and `TEMP` all point to the same writable directory, which Virgo removes when the command finishes.
- On native Windows, use `TMPDIR` (`$env:TMPDIR` in PowerShell) for files Virgo removes when the command finishes. `TEMP` and `TMP` point to the AppContainer session's shared temp directory (`$env:TEMP` in PowerShell or `%TEMP%` in `cmd` for files needed later in that session).

Put temporary files in a writable workspace path only if they must persist across calls, and remove them after their last use.

## Platform backends and honest differences

- **Linux (Tier 1 — `bubblewrap`)**: Requires system `bwrap` and unprivileged user namespaces (`--unshare-all --unshare-user --disable-userns --cap-drop ALL`, with `--info-fd` startup acknowledgement and no `libseccomp` runtime dependency). Mounts the host filesystem read-only (`--ro-bind / /`) with real read-only `$HOME` so user-installed toolchains (`~/.cargo`, `~/.rustup`, `~/.local`, `nvm`, `pyenv`, etc.), `AF_UNIX` local sockets, `AF_NETLINK`, and `io_uring` work seamlessly, while masking high-sensitivity credential paths (`--perms 000 --tmpfs` or empty read-only file mounts) and mounting the workspace, session cache, and per-command `TMPDIR` writable. Existing unapproved `.virgo` directories are bind-mounted read-only; creating a previously absent `.virgo` inside Shell is a Linux bind-mount limitation, while Broker file tools and untrusted project settings stripping still protect it.
- **macOS (Tier 1 — Seatbelt)**: Probes `/usr/bin/sandbox-exec` once per executor and launches commands directly in a dedicated POSIX process group (`HostProcess`, cleaning up same-process-group children via `waitid(WNOWAIT)` / `kqueue` + `os.killpg`). Allows read-only host path access (`/` and read-only `$HOME`), grants writes and local `AF_UNIX` sockets inside the workspace, session cache, and per-command `TMPDIR`, write-denies unapproved `.virgo` (both existing and absent), and hard-denies all high-sensitivity credential paths. A descendant that explicitly calls `setsid()` or changes process groups is not reaped automatically (same as POSIX Host commands).
- **Native Windows (Tier 1 — Standard AppContainer `windows-appcontainer`)**: Runs unelevated on local NTFS and Windows 11 ReFS Dev Drive volumes using a session-level single AppContainer SID, single-call OS-propagated inheritable ACEs, automatic read-only grants for `.venv` base Python and user-owned `PATH` toolchains, Job Object (`KILL_ON_JOB_CLOSE`) process-tree cleanup, a session-local `DefineDosDeviceW` virtual drive when workspace ancestors lack `S-1-15-2-1` (such as `C:\Users`), and a write-ahead JSON journal with automatic startup crash recovery. Existing unapproved `.virgo` is protected via `protect_readonly_path()` (`SE_DACL_PROTECTED` + explicit `ALLOW RX`) and automatically restored if approved mid-session. Private user directories are denied by default NTFS ACLs (`$HOME` cannot be used as a workspace), and **localhost/loopback (`127.0.0.1` / `[::1]`) remains blocked** in non-admin AppContainer. See [Native Windows sandbox](windows-sandbox.md) for requirements and caveats.
- **Windows + WSL2 (Tier 1)**: Uses the Linux `bubblewrap` backend inside WSL2; recommended when older Windows builds, Linux toolchains, or sandboxed localhost/loopback access are needed. See [WSL2 setup](wsl2.md).

## Broker tools, output storage, and trusted integrations

- **File tools** run in the Broker directly against `PermissionPolicy` (with no separate OS sandbox helper process), keeping cold start under 5 seconds and per-`read` latency constant regardless of workspace size.
- **Command outputs** are piped to the Broker's session-persisted `OutputStore` under `<VIRGO_HOME>/outputs/session-<id>` (readable via `read_output` after session resume, cleaned up on session trash and by a 7-day TTL; untruncated foreground commands leave no spool files behind).
- **Trusted user integrations** (Python extensions, command hooks, and stdio MCP servers) run on **Host**; trust is established when you install them or trust a project (`extensions.trustedProjects` / `--trust-project-extensions`). For URL-based MCP servers, the Host client connects to the configured endpoint and the server executes its tools. Untrusted project `hooks`, `mcpServers`, `.virgo/mcp.json`, `providers`, and `extensions` are stripped before merging onto user settings.
