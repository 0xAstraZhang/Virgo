# Native command sandbox

[Configuration](../reference/configuration.md) · [简体中文](../../zh-CN/guides/sandbox.md)

## Enable and inspect

Native isolation is opt-in. The default `disabled` preserves existing execution; it does not claim OS protection. Select an envelope at startup:

```bash
uv run virgo --sandbox workspace-write
uv run virgo --sandbox read-only
```

User settings (`$VIRGO_HOME/settings.json`, normally `~/.virgo/settings.json`) can set:

```json
{"sandbox": {"mode": "workspace-write", "network": "restricted"}}
```

Project `sandbox` settings are ignored with a notice. An explicit startup override wins over user settings. Unknown modes, keys and network values fail configuration. `/sandbox` displays the requested mode and discovered launcher; it does not change permissions or certify that the host kernel permits isolation. Every launch checks its native boundary before releasing the command; Windows also verifies the actual suspended process token and Job assignment.

## Execution boundaries

`workspace-write` requests a writable originating workspace and read-only interpreter roots. Linux/macOS expose their documented system roots; Windows uses object ACLs with ambient LPAC reads, described separately in [Windows command sandbox](windows-sandbox.md). `read-only` also makes the workspace read-only. Each command gets private writable scratch and a private `HOME`. Output logs belong to `.virgo/outputs` under the originating workspace root, including commands run from a nested directory. The broker validates the working directory and output paths before spooling and opens the output directories without following symbolic links; it retains the exact output-log descriptor. The child environment contains only `PATH`, locale/timezone/terminal variables, private home/temp paths and `VIRGO=1` (Windows also supplies fixed native runtime variables); provider keys and other inherited credentials are not forwarded.

The only supported active network policy is `restricted`. Linux uses a private network namespace and a seccomp filter that denies sockets, including pathname Unix sockets, and io_uring. macOS uses a deny-by-default Seatbelt profile without a network grant. The Windows implementation requests an LPAC without network capabilities; its current verification status is recorded in the Windows guide. Disabling isolation is an explicit startup choice, not an approval result or automatic retry.

Foreground shell tools, model-requested background commands and child-runtime shell tools use the same launcher. The workspace comes from the originating runtime, not the currently selected conversation or a child's replacement working directory. Plan and read-only child restrictions narrow each new launch to read-only. Already running processes keep their launch envelope; mode changes do not retroactively revoke their rights.

An active sandbox also prevents host execution during shell discovery and selection. Startup configuration, PATH candidates, cached choices and `/shell` commands use executable-path checks without running version probes. The version remains `unknown`; the actual isolated launch determines whether the selected interpreter can execute. A missing backend never causes a host-side version probe. See [command shells](shells.md) for the resulting version and compatibility reporting.

`accept-all`, allow rules, model review and human approval do not disable an active sandbox. Missing launchers/libraries, unsupported platforms, a denied namespace or a rejected Seatbelt profile return `sandbox_unavailable` without running the payload natively. A successful probe alone does not establish that the actual launch succeeded: Linux/macOS run a fixed Python launcher inside the actual envelope, with isolated startup and a pipe acknowledgement that confirms command exec. Windows creates the actual process suspended, verifies its token and Job assignment, then resumes it once. Native setup failures before resume are reported separately. Windows has no payload-start acknowledgement: a later DLL or runtime initialization failure is reported as the process exit, like other nonzero exits. Neither path guesses from stderr text. Timeouts and cancellation retain their separate statuses, and potentially partial operations are not automatically replayed. Shell results include the effective mode and workspace; background job results also retain backend metadata.

## Host requirements and limits

Linux requires a root-owned system `bwrap` supporting `--disable-userns` and `--ro-bind-fd`, system `libseccomp.so.2`, and permission to create the required namespaces. Protected paths use pinned source descriptors and bubblewrap's inode-verified read-only mounts; raw symlink paths are not used as protected mount sources. An older backend without the required options fails closed. The implemented seccomp architectures are x86-64 and AArch64.

macOS requires the system `/usr/bin/sandbox-exec`, `/bin/launchctl` and `/usr/bin/env`, a user launchd domain that accepts Background jobs, and the Darwin process-identity, versioned-signal and coalition-accounting interfaces. These private interfaces are checked at runtime; missing support rejects execution. Each command uses a unique temporary job, without installing a persistent LaunchAgent or enabling restart. The Windows backend and its current validation limits are documented in [Windows command sandbox](windows-sandbox.md). An unavailable boundary fails closed; `disabled` keeps the existing Windows executor.

On Linux/macOS, the read set comprises existing system roots (`/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc`, `/opt`; also `/System/Library`, `/System/Cryptexes`, `/System/Volumes/Preboot/Cryptexes/OS`, `/Library`, `/dev` and `/private/etc` on macOS), the interpreter installations, the workspace and private scratch. It is not a full host-home mount. Tools, dependency caches, certificates or SDKs outside that set may be unavailable; extra mounts and network exceptions are not implemented. A workspace containing Virgo's user credential/session directory, a system/base interpreter installation or the sandbox launcher is rejected.

An active virtual environment nested below the workspace root, such as `.venv`, is supported. Its installed commands and packages remain usable, but its interpreter directories are read-only to both shell processes and Core `write`/`edit` tools. Interpreter-directory aliases inside the workspace must not be symbolic links; normal POSIX executable links such as `.venv/bin/python` remain supported. Windows skips ungranted reparse aliases below read-only runtime roots; it rejects reparse points in the workspace. The workspace root itself cannot be the interpreter installation.

Existing root `.git`, `.virgo`, `AGENTS.md` and `CLAUDE.md` paths are protected from shell writes. A symbolic link at any of these metadata paths rejects the shell launch on Linux/macOS; it cannot add a host read mount or replace the protected directory entry. Output-directory symbolic links also reject the launch before spooling. Linux implements metadata protection with read-only mounts of existing paths; it does not protect absent metadata names from creation. macOS also excludes absent metadata names. Windows rejects workspace reparses and protects existing metadata objects through ACLs, but does not reserve absent metadata names.

On Linux/macOS, before a `workspace-write` shell launch, Virgo checks the writable workspace tree for regular files with multiple hardlinks and rejects the launch if any exist. This includes links whose other names are also inside the workspace: the link count does not identify where the other names reside. Read-only metadata and active interpreter trees are excluded; `read-only` launches can use shared files. Projects that use hardlinked writable files, for example `cp -al` copies or some package-store layouts, must replace those files with independent copies before using `workspace-write`. The traversal does not follow symbolic links and is not an atomic snapshot against concurrent trusted host changes. Native commands cannot create hardlinks from read-only sources into the writable tree. Windows setup rejects multiply linked files throughout the workspace in both active modes, including metadata, while excluding runtime roots from that rejection.

The Core `write`/`edit` tools enforce workspace/read-only/metadata/interpreter ceilings separately at application level, including on Windows. Active policies reject existing multiply linked files. They stage changes in a fresh file under protected `.virgo` and replace the destination only after a successful write or edit, so unlinking an alias after opening cannot redirect a mutation to the old inode. Failed or unchanged edits do not replace the destination, and staging files are removed. On POSIX, directory and source-file descriptors prevent symbolic-link replacement during opening; the destination must still identify the opened source before commit. Replacement retains file permission bits and text encoding/newlines, but creates a new inode and does not copy ownership, ACLs or extended attributes. Staging and destination must be on the same filesystem; cross-filesystem replacement fails without modifying the destination. These Python operations are not inside the shell's OS sandbox. Windows Core file tools retain application-level path checks without POSIX directory-descriptor traversal. The native Windows shell backend does not place those broker operations inside LPAC.

With an active policy, automatically loaded project instructions (`AGENTS.md`, `CLAUDE.md`, `.virgo/SYSTEM.md` and `.virgo/APPEND_SYSTEM.md`) are confined to the originating workspace. Ancestors outside that workspace are excluded, and replacing a child runtime's working directory cannot import another project's instructions. POSIX reads use descriptor-relative opens without following symbolic links, including when rebuilding prompts or creating children. Explicitly trusted user instructions remain available. This automatic-context boundary does not add general read grants or isolate the broker itself.

### Process lifetime and cleanup

Linux places commands in private PID namespaces. On macOS, a trusted supervisor starts the Seatbelt command in a separate launchd resource coalition. The broker checks that this identity is private and unprivileged before releasing a command. A bounded, harmless detached-child probe must also demonstrate the cleanup mechanism before the broker's first user command; the proof deadline is shorter than the probe's own lifetime, so natural expiry cannot count as successful cleanup.

With the broker running, normal completion, nonzero exit, timeout, cancellation and startup failure use the same macOS cleanup path. Removing the exact launchd job alone is insufficient: the broker also identifies remaining members by their saved resource coalition and signals them using kernel-checked PID versions. New sessions, process groups and reparenting do not change ordinary descendants' coalition membership. A process snapshot alone never establishes completion: the kernel must report no active coalition tasks and the job registration must be absent before writable scratch is removed. Different commands have separate identities.

Teardown has a bounded deadline. If process control or cleanup cannot be verified after command release, the result is `sandbox_failed`, the command may already have produced effects, and it must not be replayed. Unverified cleanup retains temporary resources instead of deleting them through garbage collection. Background jobs report cleanup failure even when cancellation was requested. When intentional termination is verified but the supervisor could not forward the command's wait status, timeout/cancellation remains accurate and the exit code is unknown (`null`), rather than fabricated.

Abrupt loss of the Virgo broker on macOS, such as `SIGKILL` or a process crash, is outside this verified cleanup path. The supervisor attempts removal of its job when the control connection disappears, but that best-effort request does not prove all detached descendants exited. Such descendants retain their Seatbelt restrictions and may continue operations permitted by their original envelope; temporary resources may remain. Resource quotas and a universal cleanup deadline under arbitrary process load are not provided.

This is not a sandbox for the broker, trusted Python extensions, project hooks, remote MCP servers, provider-hosted tools, or arbitrary direct use of low-level execution helpers by trusted integrations. A writable workspace still permits destructive changes to ordinary project files. Resource quotas, read-grant management, one-command privilege escalation and revocation of already running jobs are not provided.

## Implementation and validation

`harness/sandbox.py` binds the session policy to the caller and enforces the file-tool ceiling. `tools/sandbox.py` builds native launch envelopes and checks POSIX command-start acknowledgements; the Windows adapter verifies the suspended process before resume. `tools/macos_process.py` manages the temporary launchd job, authenticated descriptor transfer, actual child status and kernel-verified teardown. Its supervisor is trusted broker infrastructure outside Seatbelt; the command and its descendants receive the existing Seatbelt profile. `tools/windows_sandbox.py`, `windows_sandbox_acl.py` and `windows_sandbox_files.py` implement the Windows token, ACL and native path operations; the existing `WindowsProcess` owns its process lifetime. Existing shell execution, output spooling, cancellation and background-job machinery remain the callers; there is no second agent loop.

`tests/harness/test_sandbox_e2e.py` specifies assembled-session and real-process scenarios for unavailable backends, configuration trust, shell discovery and selection, file-tool enforcement, hardlink aliases, unlink and path-replacement races, indirect and symlink writes, automatic project context, child/background ownership, network and environment isolation, existing metadata, workspace-local virtual environments, output placement, actual-launch failures, exit codes, timeouts, cancellation, detached descendants, ordinary/detached `posix_spawn`, double-forked orphans and preservation of an independent background command. The native CI workflow sets `VIRGO_REQUIRE_SANDBOX_TESTS=1`, making a missing native backend a failure instead of a capability skip. Passing mocked failure cases alone does not establish OS isolation; the native report and the complete cross-platform comparison report are separate validation results.
