# Native Windows command sandbox

On native Windows, running `virgo` from your home directory uses `%USERPROFILE%\VirgoWorkspace` as the workspace. Virgo creates it on first use and reuses it on later launches. From any other directory, the current directory is the default. Use `-C` or `--cwd` to choose a workspace explicitly.

> **Status: Tier 1 (`windows-appcontainer`) on updated Windows 11 (`null.sys` Feature `60692039`).** On Windows 11 builds where `\Device\Null` grants `ALL APPLICATION PACKAGES` (`S-1-15-2-1`) read/write access (`null.sys 10.0.26100.8972+` with WIL Feature `60692039` enabled), Virgo defaults to **Workspace-Edit** (`execution.mode = "workspace-edit"`), runs **unelevated without Administrator privileges**, enforces cold-start (`<= 5s`) and O(1) per-command performance budgets, and runs blocking PR acceptance CI. On older Windows 10, older Windows 11, and stock Windows Server 2022/2025 builds where `\Device\Null` lacks `S-1-15-2-1`, Virgo defaults to **No-Limit**, shows a one-time notice with three options (**1. WSL2**, **2. No-Limit**, **3. Update Windows**), and fails closed (`windows_null_device_unavailable`) if a sandbox mode is explicitly requested. [WSL2](wsl2.md) remains a Tier 1 alternative for older Windows builds, Linux toolchains, or localhost/loopback (`127.0.0.1`) access inside sandboxed commands.

> Virgo's sandbox is a **guardrail** against occasional model mistakes—not a security boundary against malicious code, deliberate evasion, or prompt-injection attack chains. Use a container or VM for untrusted repositories. See [Execution boundaries](sandbox.md).

## How the Standard AppContainer backend works

Virgo uses **Standard AppContainer** (`src/virgo/sandbox/windows_sandbox.py`, `windows_acl.py`, `windows_files.py`):

1. **Direct Standard AppContainer launch without elevation**: Launches commands directly via `CreateProcessW` (`PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` + `HANDLE_LIST` + `JOB_LIST`) retaining `ALL APPLICATION PACKAGES` (`S-1-15-2-1`), without `CREATE_SUSPENDED` token-reverification overhead on the hot path. It never sets LPAC opt-out (`0x2000F`), never uses `CreateRestrictedToken` / `WRITE_RESTRICTED`, never edits `\Device\KsecDD` or `\Device\Null` DACLs, never creates `O:BAG:BA` admin mutexes, never mutates WindowStation/Desktop DACLs, and never writes Windows Firewall rules.
2. **Session-level single SID + automatic user toolchain grants**: Reuses one AppContainer profile and SID per `(workspace, mode)` across commands using single-call `SetNamedSecurityInfoW` OS inheritance (no per-file Python ACL walk or hardlink scan), delivering `<= 5s` cold start / first-command setup and O(1) per-command launch latency. Automatically discovers base Python in `workspace/.venv/pyvenv.cfg` (`venv/pyvenv.cfg`) and user-owned (`WRITE_DAC`) toolchains on `PATH` (`~/.cargo`, `~/.rustup`, `~/.local`, `scoop`, `go`, `%LOCALAPPDATA%\Programs\<Tool>`, `%LOCALAPPDATA%\uv`, `%LOCALAPPDATA%\Microsoft\WinGet`, etc., excluding private credential paths) and grants session-scoped read-only ACEs recorded in the crash-recovery journal. Each command receives an isolated per-command `TMPDIR` under `<AC>\Temp` cleaned immediately after Job Object (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) process-tree drain.
3. **`.virgo` metadata protection (VER-01)**: In **Workspace-Edit**, `.git`, `AGENTS.md`, `CLAUDE.md`, and `.venv` are open for normal workflows, while existing unapproved `.virgo` is protected with `protected_readonly` (`SE_DACL_PROTECTED`, preserving all non-session host ACEs so host tools and atomic editor saves never hit `WinError 5`, while restricting the session SID to `ALLOW (RX) 0x001200A9`—never `ACCESS_DENIED_ACE`, which Windows ignores for AppContainer SIDs `S-1-15-2-*`). If the user approves writing `.virgo` during the session, inherited workspace access is automatically restored.
4. **NTFS, ReFS Dev Drive, OneDrive, and ancestor virtual drive (`DefineDosDeviceW`)**: Supports both **NTFS** and **Windows 11 ReFS Dev Drive** / VHDX fixed volumes (`DRIVE_FIXED` + `FILE_PERSISTENT_ACLS`), resolves ancestor directory junctions cleanly, and ignores OneDrive cloud sync tags (`IO_REPARSE_TAG_CLOUD*`) so projects inside synced folders or Dev Drives work out of the box. When workspace ancestors (such as `C:\Users` or `%USERPROFILE%`) lack `S-1-15-2-1`, Virgo maps a session-local unprivileged drive letter (`Z:`..`M:`) to the workspace root and launches child commands with that virtual drive `cwd`.
5. **Write-ahead state journal & crash recovery**: Before mutating any DACL, Virgo atomically persists session lease state (including `owner_pid`, `owner_create_time` `FILETIME`, mapped `dos_drive`, granted roots, and pre-session DACL snapshots) to `%LOCALAPPDATA%\Virgo\sandbox-sessions\` (overrideable via `VIRGO_WINDOWS_SANDBOX_STATE_DIR`). On next startup, `recover_stale_sessions()` automatically revokes orphaned ACEs, unmaps stale drive letters, deletes orphaned AppContainer profiles, and removes completed journals idempotently.

## Requirements

- Native x64 **Windows 11** with updated `null.sys` (`10.0.26100.8972+` / WIL Feature `60692039` enabled, granting `ALL APPLICATION PACKAGES` `S-1-15-2-1` read/write access on `\Device\Null`) on a local fixed volume with persistent ACLs (**NTFS** or **ReFS Dev Drive**, no Administrator privileges required). On unsupported Windows builds (Windows 10, older Windows 11, stock Windows Server 2022/2025), Virgo defaults to **No-Limit** with guidance to choose **1. WSL2**, **2. No-Limit**, or **3. Update Windows**, and fails closed with `windows_null_device_unavailable` if `workspace-edit` or `read-only` is explicitly requested.
- Windows Filtering Platform / Firewall services (`BFE` and `MpsSvc`) running for AppContainer network isolation (if stopped, Virgo fails closed with `windows_network_isolation_unavailable`)
- Native x64 Python 3.11+ (user-owned such as `uv`-managed Python or `%LOCALAPPDATA%\Programs\Python`, or an AAP-inheriting `C:\Program Files` install—not the WindowsApps store stub) and PowerShell 7 (`pwsh`) or Windows PowerShell

## Honest platform differences & known caveats

1. **Private directories & `$HOME` workspaces**: User-profile directories (`~/.virgo`, `~/.ssh`, `~/.aws`, `Desktop`, `Documents`) lack `S-1-15-2-1` and are read- and write-denied by default NTFS ACLs without modifying `~/.virgo`. Launching Read-Only or Workspace-Edit with `$HOME` (or a directory containing private credential paths) as the workspace is rejected because granting that root would expose the user profile.
2. **Network isolation & localhost/loopback (`127.0.0.1` / `[::1]`)**: **Read-Only** (`capabilities=()`) blocks outbound TCP, UDP, DNS, and loopback via WFP. **Workspace-Edit** (`internetClient` + `privateNetworkClientServer`) allows outbound internet and private-network egress (`git`, `pip`, `uv`, HTTPS) and preserves `HTTP_PROXY` / `HTTPS_PROXY`, **but Windows blocks localhost/loopback (`127.0.0.1` and `[::1]`) in non-admin AppContainer** (exempting a package SID via `CheckNetIsolation` requires Administrator rights). Use one-shot **No-Limit** or [WSL2](wsl2.md) when a task requires local dev servers, databases, or localhost HTTP proxies.
3. **Non-AAP admin/SYSTEM-owned runtime roots (`windows_runtime_inaccessible`)**: Directories under `C:\Windows\System32` and standard `C:\Program Files` inherit `S-1-15-2-1 (RX)` automatically, and user-owned runtimes / `PATH` toolchains receive a session read-only ACE. For Virgo's own Python runtime roots (`sys.prefix` / `sys.base_prefix`) and the directly launched executable (`argv[0]`, e.g., `pwsh.exe`), if the directory lacks AAP and an unelevated user lacks `WRITE_DAC`, Virgo fails closed before launch with `windows_runtime_inaccessible` and guides you toward user-owned (`uv python install`, `%LOCALAPPDATA%\Programs\Python`) or AAP-inheriting installs.
4. **Non-existent `.virgo`**: File/directory ACLs apply only to existing filesystem objects, so Shell commands can create a previously absent `.virgo` inside a writable workspace (same limitation as Linux `bubblewrap` bind mounts). Broker file tools (`PermissionPolicy`) and untrusted project-config stripping still defend absent `.virgo`.
5. **Upstream tool & ACL inheritance caveats**:
   - **CPython 3.13 `os.mkdir(mode=0o700)` / `tempfile.mkdtemp()`**: On Windows, CPython 3.13 creates `0o700` directories with an explicit `SE_DACL_PROTECTED` DACL (`D:P(...OW)`) that omits AppContainer SIDs, locking an AppContainer child out of its own newly created `0o700` directory (for example, `pytest`'s default `cacheprovider` emits a `PytestCacheWarning` unless `-p no:cacheprovider` is passed). Standard `os.mkdir()` (default `0o777`) inherits the parent DACL cleanly.
   - **`git init` / outside-repo `git` under `C:\Users`**: Git's `strbuf_realpath()` resolves the virtual drive back to `C:\Users\...`, where ancestor `stat()` fails with `EACCES`. Inside an existing Git repository, `git status`, `git diff`, `git log`, `git add`, `git commit`, `git checkout`, and `git ls-remote` work normally.
   - **`SE_DACL_PROTECTED` workspace subdirectories**: Subdirectories with inheritance disabled before session setup are skipped by root grant (inaccessible inside AppContainer); subdirectories whose inheritance is disabled *after* setup retain an explicit SID until explicitly revoked (though profile deletion invalidates that SID for future sessions).
