# Windows command sandbox

The native x64 Windows backend requires local NTFS and the rights needed to create its AppContainer profile and temporary ACLs. The Shell tool uses PowerShell 7; the generic executor also accepts an explicit native executable. Virgo checks the suspended process's LPAC token and Job membership before release. The Job must drain before the broker revokes the temporary grants. Windows retains ambient LPAC-readable resources. A requested read deny that conflicts with those permissions is unsupported and must stop execution before payload release.

Workspace-Edit grants the command the Internet and private-network capabilities without a Virgo approval prompt. Read-Only omits these capabilities until an exact operation is approved. The host firewall and AppContainer network policy control actual outbound, inbound and host-loopback connectivity. Virgo leaves firewall rules and loopback exemptions under the user's control.

Stdio does not remove a server runtime's network dependencies. With CPython 3.13.17 and MCP SDK 2.3.0 on Windows Server 2022 and 2025, the official SDK fixture was refused under Read-Only while importing asyncio's `_overlapped` module, with `WinError 10013`. This precedes the event loop's TCP loopback wakeup. On both hosts, the same fixture initialized and completed a real tool call and workspace write under Workspace-Edit using `ProactorEventLoop`.

The [mode-specific native reports](https://github.com/0xAstraZhang/Virgo/actions/runs/44492367019) record both outcomes in the `official_mcp_sdk` JUnit property. Each mode kept its original network policy, and the Read-Only refusal published no tools and made no Host retry. The overall SDK result is `runtime_limited`; the synchronous server's complete isolation checks also passed. Virgo does not add network capabilities or loopback exemptions to start Python.

Per-operation filesystem access uses the exact existing object for a file and the specified tree for a directory. An unavailable path or an ACL that cannot be installed refuses the operation. The broker does not request elevation.

Built-in file tools execute in the same native boundary through a captured Filesystem Helper. Atomic Write/Edit stage within the destination directory, so they require an explicit directory write grant. Replacement files inherit that directory's ACL; the old file's custom explicit DACL is not copied. The helper uses retained no-reparse handles and atomic native rename without obtaining Broker ACL privileges. The host retains handle-based opens only for native ACL installation and revocation; the former Broker file replacement, output creation and DACL-copy APIs are removed. [Helper protocol and output ownership](../development/filesystem-helper.md)


Read-denied trees receive no read grants, and the ordinary write-restricting SID prevents their mutation. Package and capability SIDs do not enforce a read deny against an ambient LPAC allow. Before releasing the suspended process, Virgo checks its actual token against the security descriptors of every retained denied file and directory, including descendants. It also checks ordinary file and directory inheritance for denied directories. If `FILE_READ_DATA` or directory listing remains allowed, launch fails with `unsupported_read_deny` and the affected path; there is no host fallback or payload replay. This is an unsupported policy result, not successful read-deny enforcement.

The native acceptance case deliberately grants a private file ambient `ALL RESTRICTED APPLICATION PACKAGES` access. It requires this precise pre-release failure, an untouched payload marker and restored ACLs. Separate native cases must still launch helpers and commands successfully under supported policies and verify private-storage denial. Write-denied runtime and metadata trees stay read-only. ACL cleanup removes only the current execution's identities and restores the inheritance state it changed.

A broad HOME grant excludes the shared AppContainer `Packages` tree and grants no reads to other profiles. The executor checks denied objects and their inheritance before granting payload execution; its own private profile receives protected inheritance. User-specified deny rules cannot be overridden by this internal profile grant. Unknown profile layouts, unsupported ambient reads, or a policy that denies the process's own scratch directory fail before the payload starts.

Ordinary grant walks skip descendant reparse points without following or granting their targets. Explicit workspace, cwd, grant and deny roots still reject reparse points. Existing recursive hardlink validation remains: every link to a writable inode must lie within this execution's writable scope. These rules can still reject particular home trees whose ACLs or files cannot be safely granted. Real native acceptance covers the requested boundary; generating a policy alone does not validate Windows isolation.
