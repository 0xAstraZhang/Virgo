# Native Windows command sandbox

> **Status: Tier 1 (`windows-appcontainer`).** Native Windows defaults to **Workspace-Edit** (`execution.mode = "workspace-edit"`), runs **unelevated without Administrator privileges**, enforces cold-start (`<= 5s`) and O(1) per-command performance budgets, and runs blocking PR acceptance CI. [WSL2](wsl2.md) remains a Tier 1 alternative if you prefer Linux toolchains or need localhost/loopback (`127.0.0.1`) access inside sandboxed commands.

> Virgo's sandbox is a **guardrail** against occasional model mistakes—not a security boundary against malicious code, deliberate evasion, or prompt-injection attack chains. Use a container or VM for untrusted repositories. See [Execution boundaries](sandbox.md).

## How the Standard AppContainer backend works

Virgo replaces the legacy Administrator-only LPAC implementation with **Standard AppContainer** (`src/virgo/sandbox/windows_sandbox.py`, `windows_acl.py`, `windows_files.py`):

1. **Standard AppContainer without elevation**: Launches commands via `CreateProcessW` (`CREATE_SUSPENDED` + `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` + `HANDLE_LIST` + `JOB_LIST`) retaining `ALL APPLICATION PACKAGES` (`S-1-15-2-1`). It never sets LPAC opt-out (`0x2000F`), never uses `CreateRestrictedToken` / `WRITE_RESTRICTED`, never edits `\Device\KsecDD` or `\Device\Null` DACLs, never creates `O:BAG:BA` admin mutexes, never mutates WindowStation/Desktop DACLs, and never writes Windows Firewall rules. Suspended tokens are verified (`TokenIsAppContainer == 1`, package/capability SID match, empty `TokenRestrictedSids`, `S-1-15-2-1` granted, Everyone-only denied) before `ResumeThread`.
2. **Session-level single SID + OS-propagated inheritable ACEs**: Reuses one AppContainer profile and SID per `(workspace, mode)` across commands using single-call `SetNamedSecurityInfoW` OS inheritance (no per-file Python ACL walk or hardlink scan), delivering `<= 5s` cold start / first-command setup and O(1) per-command launch latency. Each command receives an isolated per-command `TMPDIR` under `<AC>\Temp` cleaned immediately after Job Object (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) process-tree drain; `TEMP`/`TMP` (rewritten by Windows AppContainer to `<AC>\Temp`) are session-scoped and deleted when the session closes.
3. **Control metadata protection (VER-01)**: Existing `.git`, `.virgo`, `AGENTS.md`, `CLAUDE.md`, and read-only subpaths are protected with `protected_readonly` (`SE_DACL_PROTECTED`, preserving all non-session host ACEs so host `git` and atomic editor saves never hit `WinError 5`, while restricting the session SID to `ALLOW (RX) 0x001200A9`—never `ACCESS_DENIED_ACE`, which Windows ignores for AppContainer SIDs `S-1-15-2-*`). The writable workspace root omits `FILE_DELETE_CHILD` (`0x40`) and applies `DELETE` (`0x00010000`) inherit-only so protected children cannot be deleted or renamed through parent directory rights.
4. **Ancestor-directory virtual drive (`DefineDosDeviceW`)**: When workspace ancestors (such as `C:\Users` or `%USERPROFILE%`) lack `S-1-15-2-1`, Virgo maps a session-local unprivileged drive letter (`Z:`..`M:`) to the validated canonical workspace root and launches child commands with that virtual drive `cwd`. This avoids `C:\Users` ancestor-stat failures in `pwsh`, `powershell.exe`, `cmd dir`, and `pytest` collection.
5. **Write-ahead state journal & crash recovery**: Before mutating any DACL, Virgo atomically persists session lease state (including `owner_pid`, `owner_create_time` `FILETIME`, mapped `dos_drive`, granted roots, and pre-session DACL snapshots) to `%LOCALAPPDATA%\Virgo\sandbox-sessions\` (overrideable via `VIRGO_WINDOWS_SANDBOX_STATE_DIR`). On next startup, `recover_stale_sessions()` automatically revokes orphaned ACEs, unmaps stale drive letters, deletes orphaned AppContainer profiles, and removes completed journals idempotently.

## Requirements

- Windows 10/11 or Windows Server (x64) on a local **NTFS** volume with persistent ACLs (no Administrator privileges required)
- Windows Filtering Platform / Firewall services (`BFE` and `MpsSvc`) running for AppContainer network isolation (if stopped, Virgo fails closed with `windows_network_isolation_unavailable`)
- Native x64 Python 3.11+ (user-owned such as `uv`-managed Python or `%LOCALAPPDATA%\Programs\Python`, or an AAP-inheriting `C:\Program Files` install—not the WindowsApps store stub) and PowerShell 7 (`pwsh`) or Windows PowerShell

## Honest platform differences & known caveats

1. **Private directories & `$HOME` workspaces**: User-profile directories (`~/.virgo`, `~/.ssh`, `Desktop`, `Documents`) lack `S-1-15-2-1` and are read- and write-denied by default NTFS ACLs without modifying `~/.virgo`. Launching Read-Only or Workspace-Edit with `$HOME` (or a directory containing `~/.virgo`) as the workspace is rejected because granting that root would expose the user profile.
2. **Network isolation & localhost/loopback (`127.0.0.1` / `[::1]`)**: **Read-Only** (`capabilities=()`) blocks outbound TCP, UDP, DNS, and loopback via WFP. **Workspace-Edit** (`internetClient` + `privateNetworkClientServer`) allows outbound internet and private-network egress (`git`, `pip`, `uv`, HTTPS), **but Windows blocks localhost/loopback (`127.0.0.1` and `[::1]`) in non-admin AppContainer** (exempting a package SID via `CheckNetIsolation` requires Administrator rights). Use one-shot **No-Limit** or [WSL2](wsl2.md) when a task requires local dev servers, databases, or local HTTP proxies.
3. **Non-AAP admin/SYSTEM-owned runtime roots (`windows_runtime_inaccessible`)**: Directories under `C:\Windows\System32` and standard `C:\Program Files` inherit `S-1-15-2-1 (RX)` automatically, and user-owned runtimes receive a single session read-only ACE. For Virgo's own Python runtime roots (`sys.prefix` / `sys.base_prefix`) and the directly launched executable (`argv[0]`, e.g., `pwsh.exe`), if the directory lacks AAP and an unelevated user lacks `WRITE_DAC` (for example, secondary-drive admin-owned Conda installs, junctions to secondary drives, or inheritance-broken `Program Files` MSI installs), Virgo fails closed before launch with `windows_runtime_inaccessible` and guides you toward user-owned (`uv python install`, `%LOCALAPPDATA%\Programs\Python`) or AAP-inheriting installs. Arbitrary third-party binaries invoked indirectly *inside* a shell script from non-AAP admin directories are not pre-probed and will receive standard Windows access-denied errors inside the child.
4. **Non-existent protected names**: NTFS ACLs apply only to existing filesystem objects, so Shell commands can create a previously absent `CLAUDE.md` or `.virgo` inside a writable workspace (same limitation as Linux `bubblewrap` bind mounts). Broker file tools (`PermissionPolicy`) and untrusted project-config stripping still defend absent protected names.
5. **Upstream tool & NTFS inheritance caveats**:
   - **CPython 3.13 `os.mkdir(mode=0o700)` / `tempfile.mkdtemp()`**: On Windows, CPython 3.13 creates `0o700` directories with an explicit `SE_DACL_PROTECTED` DACL (`D:P(...OW)`) that omits AppContainer SIDs, locking an AppContainer child out of its own newly created `0o700` directory (for example, `pytest`'s default `cacheprovider` emits a `PytestCacheWarning` unless `-p no:cacheprovider` is passed). Standard `os.mkdir()` (default `0o777`) inherits the parent DACL cleanly.
   - **`git init` / outside-repo `git` under `C:\Users`**: Git's `strbuf_realpath()` resolves the virtual drive back to `C:\Users\...`, where ancestor `stat()` fails with `EACCES`. Inside an existing Git repository, `git status`, `git diff`, `git log`, `git add`, `git commit`, and `git ls-remote` work normally.
   - **`SE_DACL_PROTECTED` workspace subdirectories**: Subdirectories with inheritance disabled before session setup are skipped by root grant (inaccessible inside AppContainer); subdirectories whose inheritance is disabled *after* setup retain an explicit SID until explicitly revoked (though profile deletion invalidates that SID for future sessions).
